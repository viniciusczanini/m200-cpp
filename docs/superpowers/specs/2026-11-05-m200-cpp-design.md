# C++ restrito para Schneider TM200CE40T

Data: 2026-11-05. Estado: implementação experimental autorizada pelo usuário em 2026-11-05. Windows oficial e CLP serão disponibilizados no futuro via SSH; o usuário pediu desenvolver e testar o máximo localmente agora.

## Objetivo e contrato de entrega

Programar o TM200CE40T em um subconjunto de C++, com uma biblioteca específica para esse controlador. Gerar um projeto que o EcoStruxure Machine Expert Basic abra, mostre em Ladder e compile. A transferência ao CLP continua sendo feita pelo software oficial.

O usuário quer que construções incompatíveis sejam recusadas na compilação. Isso exige uma lista explícita de recursos aceitos, alocação estática e diagnóstico conservador: uma construção desconhecida nunca será ignorada ou aproximada silenciosamente.

Compatibilidade será definida por uma combinação identificada de modelo, firmware, nível funcional, versão/build do Machine Expert Basic, template, compilador e biblioteca. Não significa compatibilidade automática com versões futuras, nem comprovação elétrica ou temporal no equipamento físico.

## Evidências verificadas

- O guia oficial EIO0000003281.04 documenta `.smbp` para projetos, `.smbe` para exemplos/templates e `.smbf` para importar/exportar POUs e funções.
- O mesmo guia, páginas 48–51, documenta a representação interna IL e a reversibilidade IL/Ladder. Nem toda sequência IL é reversível. Blocos funcionais têm estrutura e ordem obrigatórias, incluindo `BLK`, `OUT_BLK` e `END_BLK` quando aplicáveis.
- Arquivos públicos reais `.smbp` inspecionados contêm XML com `ProjectDescriptor`, `SoftwareConfiguration`, POUs, `RungEntity`, `InstructionLines`, `LadderElements` e `HardwareConfiguration/Plc/Cpu`. Há exemplos com IL e Ladder juntos e exemplos com apenas IL em certos rungs.
- Foram encontrados projetos públicos M200C24R e M200CE24R, mas nenhum template verificado do TM200CE40T. Esses arquivos são evidência do formato, não prova de compatibilidade com nosso alvo. O número `ProjectVersion` do XML não deve ser confundido com a versão comercial do editor.
- Não foi localizado nesta pesquisa um XSD público que estabeleça sozinho todo o contrato do projeto. XML bem formado não comprova aceitação pelo editor.
- O usuário informou que ainda não tem o Machine Expert Basic instalado. A versão oficial consultada é V1.4 Build 484 para Windows 10/11.

## Abordagens e decisão proposta

1. **Projeto `.smbp` completo, baseado em template oficial do alvo, com IL reversível e Ladder coerentes.** Atende ao fluxo pedido: abrir o arquivo e visualizar o programa. É a abordagem recomendada pelo assistente e ainda depende da aprovação deste desenho.
2. **Blocos `.smbf` para importar em um projeto existente.** É uma possível ferramenta auxiliar, mas acrescenta montagem manual de projeto e configuração. Não será a entrega principal.
3. **Somente texto IL para colar no editor.** Útil para diagnóstico, mas não cumpre a entrega de um projeto pronto para abrir em Ladder.

Para a linguagem de origem, a proposta é analisar C++ com Clang e restringir a árvore sintática aceita. Um parser baseado em substituição textual não é adequado para garantir tipos, escopos, precedência e rejeição de construções desconhecidas. Traduzir LLVM IR genérico acrescentaria operações e transformações cuja reversibilidade em Ladder é mais difícil de controlar.

Proposta técnica do assistente: CLI em Python, biblioteca de cabeçalhos C++ e frontend Clang com versão identificada. O compilador deve executar diretamente no macOS e, depois, em Linux/Windows. A implementação não depende de um serviço remoto.

A emulação de aplicativos x86/x64 do Windows ARM não abrange drivers x86/x64. ## Arquitetura

`fonte C++ + biblioteca → Clang AST → validação semântica → IR tipada por ciclo → IL reversível + layout Ladder → projeto candidato → validação oficial → artefato verificado`

- O frontend preserva localização de origem para erros e comentários dos rungs.
- A IR explicita leituras, escritas, condições, estado persistente entre ciclos e atualização de blocos temporizados.
- O alocador possui um único mapa para bits, palavras e valores de duas palavras. Sobreposições entre `%MW`, `%MD` e `%MF` devem ser contabilizadas.
- O backend usa uma representação única para produzir IL e o layout Ladder correspondente. Não manter dois geradores sem uma verificação de equivalência.
- O template precisa ser criado/salvo pelo editor para **TM200CE40T**, sem proteção por senha, na versão aprovada. Não adaptar um M221 ou M200 de outro modelo trocando apenas o campo de referência.
- O projeto conserva configuração de hardware, versão, nível funcional, objetos, comentários e símbolos coerentes com o programa. Metadados que mudam entre versões são tratados pelo perfil do backend.
- A saída inclui projeto, mapa de memória, mapa fonte/rung, uso de recursos e identificação das ferramentas. O nome final do comando fica a cargo do implementador.

## Semântica de execução proposta

A entrada de execução é `void scan()`, chamada uma vez por ciclo da tarefa mestre. Não há `main()` com laço infinito de aplicação. O usuário escreve operações sequenciais C++ dentro desse ciclo.

- Cada ciclo captura as entradas usadas uma vez. Não haverá acesso imediato a entradas/saídas nesta versão.
- Atribuições em C++ têm o efeito sequencial esperado para as operações aceitas. Leituras posteriores de uma variável veem sua última atribuição naquele ciclo. O compilador usa temporários/versões intermediárias para preservar isso, mesmo quando o Ladder físico requer mais rungs.
- Leituras de uma saída usam sua imagem lógica; escritas físicas são consolidadas ao final da tarefa. Uma leitura antes da primeira atribuição vê a imagem do ciclo anterior, inicializada conforme o contrato de partida.
- Globais mutáveis preservam valor entre scans. Na primeira versão, globais não retidas são reinicializadas no primeiro scan de cada entrada em RUN. Retenção entre reinícios exige declaração explícita na biblioteca. Esse comportamento deve constar no manual e nos testes.
- Valores locais comuns são inicializados em cada scan; variáveis locais estáticas, inicialmente, serão recusadas para reduzir ambiguidades.
- Cada instância de temporizador, clock ou detector de borda deve ser atualizada exatamente uma vez por scan. Chamadas omitidas por um `if` ou repetidas no mesmo ciclo são recusadas na primeira versão; habilitação é um parâmetro explícito do bloco.
- A biblioteca implementa espera por estado e temporizadores, sem bloquear a tarefa. Clocks têm fase inicial, reset e habilitação definidos. Seu período efetivo e jitter dependem da resolução e do scan; não prometer precisão maior que a comprovada no hardware.
- Inicialmente haverá uma tarefa mestre, sem tarefas periódicas/de evento concorrentes nem escrita assíncrona de variáveis pelo supervisório. Modbus exige um contrato posterior de propriedade e atualização de dados.
- STOP e exceções usam saídas de fallback configuradas. A lógica de início/reset e a retomada após falta de energia serão explícitas. O compilador não transforma este CLP em controlador de segurança funcional.

## Subconjunto e biblioteca

O primeiro marco valida somente um programa digital mínimo. A primeira versão útil acrescenta gradualmente:

- `bool`, inteiros de largura fixa aprovados, constantes, variáveis locais/globais, expressões booleanas, comparações, atribuições e `if/else`.
- Aritmética inteira somente para operações cujo comportamento de promoção, sinal, largura e conversão esteja implementado e testado. Valores/intervalos não comprovadamente representáveis são recusados; não permitir truncamento silencioso. Divisão e deslocamentos entram apenas com prova das pré-condições, ou permanecem fora da primeira versão.
- Funções auxiliares com grafo de chamadas acíclico, argumentos/retorno suportados e expansão limitada. Funções arbitrárias da biblioteca padrão são recusadas.
- Acesso tipado aos 24 canais de entrada e 16 de saída, com índices constantes e diagnóstico fora da faixa.
- Temporizadores TON/TOF/TP, clock, bordas de subida/descida, contadores e estado retido, cada recurso liberado somente após validar seu padrão de emissão no editor e no simulador.

Inicialmente ficam fora: heap, ponteiros/referências arbitrárias, recursão, exceções, RTTI, threads, chamadas de SO, espera bloqueante, assembly e qualquer nó AST não aprovado. Loops ficam fora do primeiro marco; um `for` com limites constantes pode ser adicionado depois por expansão estática com teto de tamanho. Não aceitar `while` dependente de entradas. Arrays, structs, enums e templates da aplicação podem ser adicionados depois; templates internos da biblioteca precisam de tratamento explícito.

A sintaxe final da API é decisão do implementador, mantendo C++ válido e tipos verificáveis pelo Clang. Deve permitir expressar um clock e uma saída em poucas linhas sem expor endereços de temporários ou numeração manual de timers. Exemplos serão rotulados como proposta até existir uma implementação testada.

## Limites e falhas de compilação

O guia EIO0000002019.06 informa, para o M200: 1024 bits `%M`, 8000 palavras `%MW`, 255 timers `%TM` e 255 contadores `%C`. O alvo tem 24 entradas e 16 saídas. Reservas do compilador também consomem esses totais. Níveis funcionais/firmware podem impor restrições adicionais.

O guia informa salvamento automático de `%MW0..2999` e `%M0..499` em falta de energia. O alocador deve distinguir retenção explícita de estado transitório e inicializá-los conforme o contrato; uma variável comum não pode herdar retenção acidental.

Também serão verificados tamanho do programa, rungs, largura/profundidade de Ladder, blocos disponíveis, constantes de tempo representáveis, conflitos de periféricos e regras de reversibilidade. Os limites que não estiverem comprovados no perfil são tratados como desconhecidos, e não como ilimitados.

Tempo de execução é um limite separado: rejeitar fluxo sem limite estático e registrar o tamanho/custo das expansões. Um número de instruções ou teste no simulador não prova o pior tempo de scan no CLP. Não publicar garantia temporal sem modelo conservador validado no alvo físico. O diagnóstico deve distinguir limite lógico de recursos, compatibilidade do editor e requisito temporal não verificado.

## Compatibilidade e testes de aceitação

1. **Prova do formato antes da implementação ampla:** instalar/abrir o editor em Windows, criar template TM200CE40T, salvar/reabrir e compilar um programa simples; registrar versão/build e nível funcional. Sem CLP conectado.
2. Inspecionar uma cópia do template e gerar uma modificação mínima. O editor precisa abrir sem reparo inesperado, apresentar Ladder coerente, compilar sem erros/advisories de reversibilidade e salvar/reabrir mantendo a lógica.
3. Validar cada padrão liberado: contatos, bobinas, condições, atribuições e, depois, blocos de biblioteca. Verificar IL e Ladder após o round trip pelo editor.
4. Testar localmente o frontend com casos aceitos e rejeitados; recursos desconhecidos devem falhar com linha/coluna. Testar exaustão de memória e objetos, aliases, ordem de atribuição e inicialização.
5. Comparar, para sequências de entradas e tempo, a execução C++ de referência, um executor da IR/IL e o simulador oficial. O executor próprio precisa de oráculos e casos independentes; concordância de dois componentes que compartilham o mesmo erro não basta.
6. Testar os cenários de bordas, clock, reset, enable, limites de tempo, STOP/RUN e reinício. Partes não representadas pelo simulador são marcadas para teste físico.
7. Uma geração em modo de desenvolvimento pode produzir um **candidato não verificado**. O comando de entrega verificada só termina com sucesso após o projeto exato passar pelo editor oficial e pelos testes de simulação requeridos. A evidência fica vinculada ao hash dos bytes gerados e às versões do perfil/ferramentas; qualquer mudança invalida esse resultado. Um arquivo de manifesto sozinho não substitui executar os testes.
8. Transferência e teste físico são marcos separados, usando o software oficial e autorização do usuário para energizar/acionar cargas. Não atualizar firmware nem escrever no CLP como parte desta pesquisa.

Todos os testes/builds serão locais. Não criar nem ativar GitHub Actions ou pipelines remotas. Uma bateria finita de testes não é prova matemática universal de correção do compilador; a garantia de entrega é delimitada pelo subconjunto aceito, perfil aprovado e validação oficial do artefato.
